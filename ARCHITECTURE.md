# Architecture decision: drop the single-file constraint

**Decided by Stewart, 24 August 2026.**

> "This is quickly getting bigger than an HTML document. I say we scrap the HTML document
> for the time being and just develop this like we would anything else without that
> constraint."

---

## What changed and why

`the-vanishing-v2.html` is 4,741 lines and about 325 KB, and it already fails the constraint
it was built under: it loads `assets/photos/*` by relative path, so it is not actually a
single portable file. Case data, scoring logic, rendering, the graph engine, the analyst
panel and the design system all live in one document. Adding a case means editing a
JavaScript literal inside a script tag inside an HTML file, and there is no way to validate
the data without opening a browser.

**The single-file constraint has stopped buying anything and started costing.**

## Target structure

Adopt The Legacy Program Dashboard's layout. This is not borrowing from a sibling project by
coincidence: The Program was built on The Vanishing's own engine, schema and design system,
so this is the pattern coming home with two months of hardening on it.

```
data/           the merged dataset, machine-readable, the single source of truth
research/       per-case and per-domain source files, hand-edited
tools/          build pipeline and the verification gate
dist/           the built dashboard
assets/         photographs
notes/          research log, QA reports, design briefs
```

Build pipeline, mirroring The Program's:

```
python tools/merge.py            # research/*.json -> data/
python tools/build_dashboard.py  # data/ -> dist/the-vanishing.html
python tools/verify.py --idempotent
```

## What this unlocks

| Gain | Why it matters here |
|---|---|
| **Case data becomes editable without touching rendering code** | Weekly sweeps stop being HTML surgery |
| **Per-claim tiering** (1 documented / 2 sourced / 3 inference) | The biggest single credibility upgrade available. Today a Tier A case can contain an unmarked inference and nothing catches it. See `PORT-FROM-THE-PROGRAM.md` section 5. |
| **Sources arrays attached to claims** rather than a bibliography | Every assertion individually auditable |
| **An automated verification gate** | Dead URLs, dangling references, tier violations, date inconsistencies caught before they ship rather than during adversarial review |
| **Outcome-type field** | Lets the neutralisation frame be recorded as data instead of as a thumb on the scores. See `THESIS-NOTES.md`. |
| **Diffable data** | Git history shows what changed about a case, not that a 325 KB blob changed |

## The rule that has to come with it

The Program learned this the hard way and wrote it down: **`verify.py` passing is the
definition of shippable, and every check in it must itself be tested** against input it is
required to reject. Three of The Program's first eight checks were born broken and silently
passing. A verification gate that does not fail on bad input is worse than none, because it
manufactures confidence.

## Migration order

1. Extract the case records from `the-vanishing-v2.html` into `research/cases.json`, lossless, no edits to content.
2. Stand up `tools/merge.py` and `tools/build_dashboard.py` so the current HTML can be regenerated byte-for-byte from data. **Regenerating the existing output exactly is the checkpoint** -- it proves nothing was lost in extraction.
3. Only then add per-claim tiering, sources arrays and the outcome field.
4. Then write `verify.py`, with self-tests, and make it the gate.
5. Then import from The Program per `PORT-FROM-THE-PROGRAM.md`.

Do not do 3 before 2. Extraction and schema change at the same time is how records get
silently mangled, and the whole value of this project is that its records are right.

## Retained

`the-vanishing-v2.html` stays in the repo until step 2 passes, as the reference output and
the fallback. It is the thing the rebuild has to reproduce.

The Program consumes `the-vanishing-v2.html` as a frozen build input at its own
`ref/the-vanishing-v2.html`. **That is a copy and it is pinned.** Restructuring here does
not affect The Program, and the rebuild must not assume anyone will update that copy.
